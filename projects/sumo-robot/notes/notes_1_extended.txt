10. turnLeft()

This is where differential drive becomes important.

    analogWrite(RIGHT_R_PWM, speed);
    analogWrite(RIGHT_L_PWM, 0);
}

The left motor goes backward.

The right motor goes forward.

             FRONT

         ↺           ↻
      backward     forward

LEFT  → forward
RIGHT → backward

Therefore:

LEFT  backward
RIGHT forward

turnRight:
LEFT  forward
RIGHT backward

This is called differential drive.

Your robot doesn't need a steering wheel. It changes direction by changing the relative movement of the left and right wheels.

1. The four buffers
static int frontLeftBuffer[SENSOR_SAMPLES];
static int frontRightBuffer[SENSOR_SAMPLES];
static int leftBuffer[SENSOR_SAMPLES];
static int rightBuffer[SENSOR_SAMPLES];

static int bufferIndex = 0;
First: what is an array?

In Python:

buffer = [0, 0, 0, 0]

In C++:

int buffer[4];

means:

Create space for 4 integers.

Here:

int frontLeftBuffer[SENSOR_SAMPLES];

Since SENSOR_SAMPLES = 4, this becomes conceptually:

frontLeftBuffer
[0] [0] [0] [0]

The purpose is to store the 4 most recent readings from that sensor.

For example, after several loops:

frontLeftBuffer
[520] [530] [515] [525]

Instead of trusting one instantaneous sensor reading, we can average these.

Why four separate buffers?

Because there are four independent opponent sensors.

Front-left  → frontLeftBuffer
Front-right → frontRightBuffer
Left        → leftBuffer
Right       → rightBuffer

You don't want the front-left sensor's history mixed with the right sensor's history.

2. What does static mean here?

This is important because static has different meanings depending on where you use it.

Here:

is at file scope, so static means:

This variable belongs only to Sensors.cpp. Other .cpp files cannot access it directly.

That's exactly what the comment says.

So Strategy1 cannot do:

frontLeftBuffer[0]

It doesn't know that variable exists.

It can only do:

This is good architecture.

The strategy knows:

"Give me sensor readings."

It does not need to know:

"There are four arrays, each containing four historical ADC measurements."

3. bufferIndex
static int bufferIndex = 0;

This tells us which position in the arrays should be overwritten next.

Initially:

index = 0

[ ? ][ ? ][ ? ][ ? ]
  ↑
write here

After writing:

index = 1

[520][ ? ][ ? ][ ? ]
       ↑

Then:

index = 2

[520][530][ ? ][ ? ]
             ↑

Eventually:

[520][530][515][525]

Then we go back to position 0 and overwrite the oldest value.

That's why this is called a rolling buffer.

4. averageBuffer()
static int averageBuffer(int *buffer) {
    long sum = 0;

    for (int i = 0; i < SENSOR_SAMPLES; i++) {
        sum += buffer[i];
    }

    return sum / SENSOR_SAMPLES;
}

This function exists because all four buffers need the exact same operation:

Add the four readings and divide by four.

Rather than writing the same code four times, we create one function.

The weird part: int *buffer
int *buffer

The * here means pointer.

For now, think of it as:

"Give this function access to an array of integers."

So when we later write:

averageBuffer(frontLeftBuffer)

we are effectively saying:

"Average the front-left array."

You don't need to fully understand pointers yet. You'll encounter them repeatedly in C++, and we'll build the concept properly when necessary.

5. long sum = 0
long sum = 0;

Why long instead of int?

Because we're adding numbers together.

For four sensor values it doesn't matter much:

500 + 520 + 510 + 530 = 2060

But using long gives the sum more numerical capacity.

The variable starts at zero because we're about to accumulate values into it.

6. The for loop
for (int i = 0; i < SENSOR_SAMPLES; i++) {
    sum += buffer[i];
}

This is C++'s standard counting loop.

Python equivalent:

for i in range(4):
    sum += buffer[i]

Breakdown:

int i = 0

Create i and start at 0.

i < SENSOR_SAMPLES

Keep looping while i < 4.

i++

After every iteration, increase i by 1.

So:

i = 0
i = 1
i = 2
i = 3
stop

Then:

sum += buffer[i];

is shorthand for:

sum = sum + buffer[i];
7. Returning the average
return sum / SENSOR_SAMPLES;

Suppose:

buffer = [500, 520, 510, 530]

Then:

sum = 2060

2060 / 4 = 515

So:

averageBuffer(buffer)

returns:

9. Why pre-fill the buffers?

This is one of the more important design decisions.

for (int i = 0; i < SENSOR_SAMPLES; i++) {
    frontLeftBuffer[i]  = analogRead(OPPONENT_FRONT_LEFT);
    ...
}

Suppose we didn't do this.

At startup, the arrays could effectively contain:

[0][0][0][0]

Then the first real reading is 600:

[600][0][0][0]

Average:

600 / 4 = 150

That's obviously wrong.

The sensor might actually be detecting the opponent strongly, but the smoothing system says:

150

because three slots haven't been populated yet.

Instead, initialization reads the actual sensor four times:

[600][598][603][601]

Average:

600

So the first result is immediately meaningful.

Why not just initialize them to 600?

Because we don't know what the sensor is actually seeing.

The code therefore says:

"Whatever the sensor is currently seeing, use that as the initial history."

10. readOpponentSensors()

This is the main sensor-reading function.

First:

frontLeftBuffer[bufferIndex] = analogRead(OPPONENT_FRONT_LEFT);

analogRead() asks the Arduino:

"What value is currently coming from this analog sensor?"

Conceptually:

reading = sensor.read()

The value is then placed into the current buffer position.

All four sensors do this:

                    bufferIndex
                         ↓
FL: [520][530][515][525]
FR: [410][420][415][430]
L : [100][110][105][115]
R : [700][690][710][705]

If bufferIndex == 2, the new readings replace position 2.

11. The most important line for the rolling buffer
bufferIndex = (bufferIndex + 1) % SENSOR_SAMPLES;

This is how the index wraps around.

Assuming 4 samples:

Current index    New index
     0               1
     1               2
     2               3
     3               0

Why?

Because of %.

For example:

(0 + 1) % 4 = 1
(1 + 1) % 4 = 2
(2 + 1) % 4 = 3
(3 + 1) % 4 = 0

So it creates a loop:

0 → 1 → 2 → 3 → 0 → 1 → ...

This is exactly what we want.

The buffer therefore doesn't grow indefinitely.

It always contains the latest four readings.

14. Edge sensors are different

The opponent sensors give numbers.

The edge sensors only need to answer:

"Am I seeing white?"

Therefore the result is four bools.

This expression
digitalRead(EDGE_FRONT_LEFT) == EDGE_WHITE_STATE

has two parts.

First:

digitalRead(EDGE_FRONT_LEFT)

gets the electrical state:

HIGH

or

LOW

Then:

== EDGE_WHITE_STATE

asks:

"Is what I read equal to the state we defined as white?"

== means comparison.

It does NOT assign anything.

Remember:

=   assignment
==  comparison

So:

edges.frontLeft = (...);

means:

Put the result of this comparison into frontLeft.

For example:

digitalRead() → HIGH
EDGE_WHITE_STATE → HIGH

HIGH == HIGH → true

Therefore:

edges.frontLeft = true
15. anyEdgeDetected()
bool anyEdgeDetected(EdgeReadings edges) {
    return edges.frontLeft ||
           edges.frontRight ||
           edges.backLeft ||
           edges.backRight;

|| means OR.

So this asks:

front-left white?
OR
front-right white?
OR
back-left white?
OR
back-right white?

If even one is true:

anyEdgeDetected(...) → true

→ false

This exists because the main robot loop needs a simple question:

The strategy doesn't need to manually inspect all four sensors.

The core reason for the buffers is not "because C++ needs arrays."

It's because your physical sensor readings can fluctuate:

void drive(int leftSpeed, int rightSpeed) {

  rightSpeed = constrain(rightSpeed, 0, 255);
